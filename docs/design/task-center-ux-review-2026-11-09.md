# EvalScope 任务中心与性能测试结果体验优化方案

评审日期：2026-11-09。范围：Web 任务工作区、队列状态、任务监控、性能归档、AIPerf 单次压测及前缀缓存实验结果。

## 1. 结论与评审边界

建议将现有“配置表单 + 右侧状态日志”的任务工作区，逐步调整为“任务中心 → 任务详情 → 结果分析”。优先解决任务数量与状态不可快速辨认、监控上下文不稳定、性能测试结果信息过载三个问题。AIPerf 与 EvalScope 是性能测试的不同执行后端，共用性能测试入口、结果列表和详情体系，不按后端建立独立导航。

本轮产出是评审与设计方案，未修改应用业务代码。

证据范围：

- 阅读当前 React 页面、任务组件、轮询逻辑、Flask API、内存队列与 Redis 队列实现，以及性能结果投影与测试样例。
- 启动当前 Vite 源码并在浏览器查看任务页、Performance 分页和 AIPerf 配置流程，确认首屏层级与表单占位。
- 本地 Python 环境缺少 Flask，未启动真实后端；浏览器出现的服务连接失败属于本次预览环境，不能据此判断项目部署故障。
- 多任务并行、取消竞态、结果页真实数据布局与移动端尚未完成运行时验证；以下涉及这些行为的现状结论来自源码，需在实施阶段补充验证。
- 使用仓库本地 `ui-ux-pro-max` 的 design-system、UX、chart 和 React 检索。采用其数据密集控制台、状态反馈、渐进披露、可访问性建议。检索也返回了不适用的营销落地页布局及蓝橙配色，未采纳；沿用现有 `DESIGN.md` 的双主题、紫色主色和系统字体。

## 2. 现状诊断：按用户影响排序

优先级说明：P0 表示首批必须解决的任务可理解性或结果可信度问题；P1 表示主要流程效率；P2 表示深入分析与扩展体验，不代表生产事故等级。

| 优先级 | 已确认的实现 | 用户影响 | 源码证据 |
| --- | --- | --- | --- |
| P0 | 活跃列表只展示一个总数，包含排队与执行中任务；列表标题使用 Running tasks | 无法直接回答“正在跑几个、等几个” | `ActiveTasksPanel.tsx:84–105`；`blueprints/tasks.py:244–261` |
| P0 | 行内状态主要以百分比或队列序号表达，缺少独立状态列；排队也出现 30% 宽脉冲条 | 排队容易被理解为已经开始；百分比掩盖执行/收尾/停止中等差异 | `ActiveTasksPanel.tsx:29–59` |
| P0 | 活跃接口只返回非终态任务；内存队列结束后移除记录 | 已完成或失败的任务从总览消失，无法从任务中心追溯 | `TaskQueue._run()`；`blueprints/tasks.py:list_active()` |
| P0 | 单次性能报告默认进入 runs 分页；AIPerf 质量原因仅出现在节点分页；概览中质量作为普通 basic_info 项呈现 | 用户先看到明细与图表，可能未注意到结果 partial/invalid | `PerfReportDetailPage.tsx:119–123,183–200, nodes panel` |
| P0 | 缓存实验请求与节点样本加载失败后被设为 null；矩阵子请求只保留成功项 | 加载失败、加载中和没有数据容易都表现为“—”，下一步不明确 | `CacheExperimentPage.tsx:76–99, requests/raw metrics sections` |
| P1 | 顶部活跃列表 → 任务类型 Tabs → 大块模型连接编辑器 → 新建表单和监控 3:2 双列 | 首屏由新建配置占据，已有任务监控需向下查找；活跃任务越多，监控越靠下 | `TasksPage.tsx:272–340`；`TaskRunnerShell.tsx:91–95`；浏览器确认 |
| P1 | 选中任务只有 eval/perf 两个 sessionStorage 槽，URL 只保存类型 | 无法分享一个明确任务详情链接；同类任务之间持续切换不方便 | `TasksPage.tsx:228–244`；`TaskRunnerShell.tsx:58–68`；`App.tsx` |
| P1 | 任务详情身份、配置、AIPerf 实时指标、状态、停止和日志纵向串联 | 关键状态和停止操作靠后，窄监控列承载过多信息 | `TaskRunMonitor.tsx:116–212` |
| P1 | 缓存实验页连续堆放身份预算、12 列矩阵、散点、两种对比、重复统计、子运行、节点和原始样本 | 点击子运行后详情出现在较远位置，容易失去当前选中项与对比上下文 | `CacheExperimentPage.tsx:178–341` |
| P1 | 缓存实验页 KPI 从当前加载的最多 50 组 scenario 计算，翻页重新计算 | 页面级 KPI 会随矩阵翻页改变；虽有范围说明，仍不适合成为实验总览 | `CacheExperimentPage.tsx:76–85,110–177` |
| P1 | 缓存实验状态只在挂载时获取一次 | 若运行中打开可读的部分结果，报告状态不会自动跟随执行变化 | `CacheExperimentPage.tsx:70–75`；任务 API 允许已有可读子结果生成报告链接 |
| P1 | 日志每次更新都强制滚动到底部 | 用户查看旧错误时会被新日志带走 | `LogViewer.tsx:10–16` |
| P2 | 节点页直接展示原始指标名、JSON labels、纳秒窗口、availability/boundary/reason | 数据充足，但解释与浏览成本高，难迅速判断哪个节点值得看 | `NodeWindowPanel.tsx:26–62` |
| P2 | 性能结果列表与缓存实验归档是两套展示；实验归档以 task_id、原始状态为主 | 跨单次压测与实验结果的身份识别、筛选和回溯不统一 | `PerfReportsPage.tsx:256`；`CacheExperimentArchive.tsx` |

已有能力应保留：后端任务状态较完整；活跃列表和详情均有轮询；有断连/陈旧数据提示；停止请求区分请求中与服务确认；报告链接由服务端解析；AIPerf 已保留 source/scope/count/quality 等语义；已有分位数、请求分页、节点选择、矩阵和可比性校验。优化主要在组织和表达，不需要重建执行框架。

## 3. 目标与信息架构

用户进入任务中心，应先回答四件事：

1. 目前有多少任务占用执行槽位、多少排队？
2. 哪些任务需要处理，最后更新是否可信？
3. 某个任务当前在哪个阶段，下一步能做什么？
4. 已结束任务的结果是否完整，去哪里分析？

建议路由与职责：

| 页面 | 建议路由 | 主任务 |
| --- | --- | --- |
| 任务中心 | `/tasks` | 总览、筛选、历史、选择任务 |
| 新建任务 | `/tasks/new?kind=perf&engine=aiperf` | 配置、校验、计划预览、提交 |
| 任务详情 | `/tasks/:taskId` | 状态、阶段、日志、实际提交配置、结果入口 |
| 性能测试结果 | `/performance` | 统一展示各后端的性能测试记录；按测试类型、模型、时间和状态筛选 |
| 单次/扫描结果 | 保留 `/perf-report?root_path=…&path=…` | 性能结论、分位数、请求、节点 |
| 缓存实验结果 | 保留 `/perf-experiment/:taskId` | 场景矩阵、重复轮次、对比、子运行分析 |

产品层级统一为“任务类型 → 测试类型 → 执行后端”：任务类型是模型评测或性能测试；性能测试类型是单次测试、负载扫描或缓存实验；执行后端是 EvalScope 或 AIPerf。后端名称只用于创建配置、详情元信息、可选筛选和问题排查，不作为一级菜单、结果栏目或独立产品页名称。

性能结果列表使用同一种记录展示和筛选交互，将目前独立追加的缓存实验归档纳入共同列表。现有两条详情路由可作为过渡期兼容地址；它们表达单次/扫描与实验的数据结构差异，不表达后端分区，页面通过统一的结果详情框架承载。

结果页共享报告头、质量提示、指标卡、来源说明和明细组件，按测试类型和结果能力渐进显示模块：

| 判断依据 | 显示模块 | 不具备时的处理 |
| --- | --- | --- |
| 通用性能指标 | 概览、指标、负载和配置信息 | 按实际可用字段展示，不制造数值 |
| 多个负载点 | 负载曲线与运行切换 | 单次测试不显示趋势分析 |
| 已保存请求记录 | 请求明细 | 若未保存，说明未采集；若读取失败，显示局部重试 |
| 节点采集与分析数据 | 节点指标 | 未配置时不占主分页；已配置但失败时保留原因入口 |
| 缓存实验维度 | 场景矩阵、重复轮次和基线对比 | 普通测试不展示实验模块 |
| 质量或覆盖元数据 | 质量、覆盖与限制说明 | 缺少元数据表示未提供，不能推断为完整 |

模块由可验证的测试类型、采集配置与数据能力决定，不通过 `engine === 'aiperf'` 直接决定页面结构。AIPerf 与 EvalScope 的结果先经过各自适配，再使用共同的展示契约；后端特有的原始字段保留在配置与产物中。统一展示仍需保留指标口径和可比性校验，不意味着不同后端的同名数值可以直接混算。

兼容现有 `/tasks?tab=eval|perf`：迁移后指向相应新建任务类型；保留旧 `/eval`、`/perf` 重定向。携带 model/dataset 的入口也应保留。结果返回任务详情时带 `from_task` 或明确返回链接；从历史归档打开时返回原归档位置。返回列表恢复筛选、页码和滚动位置。

## 4. 任务中心设计

### 4.1 桌面结构

```text
任务中心                                      [新建任务]
执行中 2       排队 3       待处理 1       今日完成 8
队列可连接 · Worker 信息待提供 · 最近同步 3 秒前

[进行中] [需处理] [全部历史]   搜索名称 / 模型 / ID
任务类型 ▾    执行器 ▾    状态 ▾    时间 ▾

任务 / 模型       类型·执行器     状态        进度 / 阶段      时间      操作
生产接口回归       性能·AIPerf     执行中      4/12 · 正式压测   运行8分   详情
Qwen精度基线       评测·原生       结果收尾    评测已结束        运行3分   详情
晚间负载扫描       性能·原生       排队        第1位             等待2分   取消
```

示例数值仅说明设计，不是当前任务数据。

采用“紧凑统计条 + 状态筛选 + 表格”。任务状态多、字段需要横向对齐，表格比 Kanban 更适合这一主流程；移动端转为任务摘要卡。新建任务放右上主按钮，连接和模板编辑不常驻任务中心。

### 4.2 数量口径必须固定

| 指标 | 口径 | 点击行为 | 依赖 |
| --- | --- | --- | --- |
| 执行中 | preparing + running + finalizing + cancelling；副标签列出收尾/停止中数量 | 筛选所有占用执行流程的任务 | 现有活跃列表可计算 |
| 排队 | queued | 按 queue_position 升序展示，未知位置单独标识 | 现有数据可计算 |
| 待处理 | 失败终态 + 状态待确认等按 task_id 去重；partial 结果另作质量提醒 | 打开待处理任务视图 | 完整口径需要历史接口 |
| 今日完成 | 用户本地日界内 finished_at 的 completed 任务 | 完成历史 | 历史索引与终态时间投影 |

P0 先上线“执行中 / 排队 / 状态待确认”，所有数字明确为当前活跃范围；历史接口落地后再上线“待处理 / 今日完成”。不能把“当前返回的 active 数量”用于表示今日完成或整个队列容量。

统计默认不随文本搜索变化，注明“全局”；筛选后的数量写在表格上方“显示 6 / 24 项”。如果统计请求失败，显示“状态待同步”，保留上次数据并标明时间，不置零。

任务执行槽位与压测 concurrency 是两种不同资源。前者来自任务 Worker 配置，后者来自对目标模型的请求并发；界面分别命名，不能共用“并发”一个标签。

### 4.3 列表行与排序

- 第一列：alias 为主标题，model 为副标题；短 task_id 和 endpoint 可复制，完整身份可展开。
- 类型：模型评测 / 性能压测；执行器单独显示 EvalScope / AIPerf。缓存实验作为性能任务的子类型。
- 状态：图标 + 中文标签 + 语义色，始终独立于进度列。
- 进度：有可信分母才显示百分比/计数；实验用“已完成 4 / 12 组”，同时显示当前阶段。没有进度时显示阶段和不定进度标记。
- 时间：排队显示等待时长；运行显示执行时长；终态显示结束时间。tooltip 或展开行显示绝对时间。
- 操作：行内保留“详情”和一种最相关操作，其余收进菜单。排队为“取消排队”，运行态为“停止任务”，终态为“查看结果 / 复制配置”。
- 默认进行中视图：执行流程组置顶，排队组按真实队列位置；历史默认最近结束优先。轮询不得因为进度变化重排行、抢焦点或跳页。
- 超过一屏采用分页；有真实大数据瓶颈再考虑虚拟列表。

### 4.4 队列健康反馈

现有 `/ready` 只能证明队列后端可连接，不能证明 Redis Worker 正常消费任务。首版应显示“队列可连接”，不要显示未经证明的“执行器正常”。

新增运行容量与健康契约后，再显示“2 个执行槽位，已占用 1 个；Worker 最近心跳 4 秒前”。Redis 模式要读取实际 Worker 注册与心跳，不能复用内存模式的 `EVALSCOPE_TASK_QUEUE_WORKERS` 当作集群容量。worker 缺失时应能解释“任务已排队，当前没有可用 Worker”。

暂不设计拖拽排序、暂停、提升优先级、断点续跑按钮：当前契约不提供这些调度语义。

## 5. 状态、阶段与数据质量

### 5.1 四个维度独立呈现

| 维度 | 回答的问题 | 示例 |
| --- | --- | --- |
| 执行状态 | 任务还在运行吗？ | 排队、执行中、结果收尾、已完成 |
| 当前阶段 | 正在做什么？ | 校验、生成输入、缓存预填充、正式压测、排空、导入 |
| 结果质量 | 数据是否完整可用？ | complete、partial、invalid |
| 数据新鲜度 | 当前信息还能信吗？ | 3 秒前同步、更新中断、状态待确认 |

`completed + partial` 是合法组合，应展示“执行完成 · 结果部分可用”。不能只显示绿色成功。

### 5.2 状态文案与动作

| 后端状态 | 用户文案 | 进度表达 | 操作 |
| --- | --- | --- | --- |
| queued | 排队中 | 第 N 位；位置未知就明确说明，不画固定 30% 条 | 取消排队、查看配置 |
| preparing | 准备中 | 不定进度 + 已知准备阶段 | 停止、日志 |
| running | 执行中 | 真实百分比或已完成组数 + phase | 停止、查看实时指标 |
| finalizing | 结果收尾 | “测量已结束，正在整理结果” | 查看日志；仅按后端实际支持提供停止 |
| cancelling | 正在停止 | “停止请求已发送，等待确认” | 等待、日志；防止重复提交 |
| completed | 已完成 | 结果入口 + 独立质量标签 | 查看结果、复制配置新建 |
| stopped | 已停止 | 保留已完成数量，不补到 100% | 部分结果入口（若可读）、复制配置新建 |
| error | 执行失败 | 简明错误摘要 + 原因位置 | 日志、复制配置新建 |
| unknown | 状态待确认 | 上次已知状态与同步时间 | 重新同步、查看已有产物 |

“提交中 / 服务已接受 / 提交结果待确认”属于提交交互，不应伪装成运行状态。请求超时后保留原 task_id 进行查询，避免用户点重试产生重复任务。确定被服务拒绝才允许直接重新提交。

AIPerf 的 phase 只在当前子运行内部发生；每一组可能重复 priming → profiling → draining → importing。详情采用两层：上层展示已完成子运行数，下层展示当前子运行阶段。未知或不适用阶段直接标注，不假设所有任务经过同一条流水线。

队列位置不等于预计开始时间。无历史估算依据时只展示等待时长和位置；ETA 作为后续能力，需说明估算依据与范围。

## 6. 独立任务详情

### 6.1 页面布局

```text
任务中心 / 生产接口回归
生产接口回归      [执行中] [性能·AIPerf]             [停止任务]
模型 · Endpoint · 短 ID · 已运行 8 分钟 · 3 秒前同步

已完成 4 / 12 组                         当前：负载32 / 目标80% / 第2轮
[真实组数进度条]                         正式压测 → 排空 → 导入

[概览] [日志] [实际配置] [子运行（实验任务）]
当前执行摘要 / 实时请求计数 / 采集状态
```

头部始终可见当前身份、状态与主要动作。状态不再藏在配置和实时指标后面。

概览仅呈现 3–4 个最有用的实时值，明确“客户端请求进度”与“节点共享流量”。完整指标表放到对应分页。完成后同一页面展示结果摘要和“查看结果”，不自动切走用户正在阅读的日志。

### 6.2 配置与任务身份

“实际配置”展示提交时的只读快照；工作区当前草稿和已选任务始终分离。用户改连接、切换执行器或模板，不能改变任务详情标题或停止目标。

现有 `TaskConfigSummary` 覆盖原生评测/压测字段，不能完整表达 AIPerf 实验计划。第一阶段展示已有字段并写明“配置摘要”；完整复现需新增分类型 Pydantic 快照，保存脱敏执行参数与关联计划。不要用前端当前 localStorage 草稿来补充历史任务配置。

“重新运行”首版命名为“复制配置新建”：建立新 task_id，进入配置确认，缺少密钥时要求补全。避免承诺当前不支持的原地重试或恢复。

### 6.3 日志体验

- 自动跟随默认开启；用户向上滚动后暂停跟随，显示“有 N 条新日志 · 回到底部”。
- 允许暂停/恢复显示更新，不影响后端执行；状态同步仍可继续。
- 搜索当前已加载日志；全量日志下载需要单独接口，不能把局部 tail 当完整日志。
- 首版按已有文本做级别过滤时明确解析限制；长期可增加结构化日志级别。
- 保留行号/时间（源日志有时间才展示），换行开关，复制选中内容。
- 限制前端保留的日志体量，明确“显示最近 N 行”，避免目前字符串持续追加导致大任务内存增长。

### 6.4 错误与停止

排队取消即时请求，收到后端确认才进入“已停止”。运行停止可使用轻量确认说明当前组可能不完整；不做多重弹窗。失败时保持原状态和日志，提示“停止结果未确认，重新同步”。

详情提供“执行错误 / 状态同步错误 / 日志读取错误 / 指标采集错误”四类独立反馈，不把指标采集失败等同任务失败。unknown 状态下不能直接删除或自动重跑。

## 7. 新建任务流程

新建页保留模型连接和模板复用能力，但按照实际决策顺序组织：

1. **任务类型与测试目标**：模型评测 / 性能测试；性能任务先选择单次测试、负载扫描或缓存实验，再在执行设置中选择支持该目标的后端。不展示当前后端尚不支持的可提交组合，并解释能力限制。
2. **目标连接**：默认显示已选连接摘要，点击编辑再展开完整表单。
3. **工作负载**：数据集、请求数、输入/输出、负载、缓存复用目标；高级采样和节点设置折叠。
4. **计划与提交**：展示子运行数量、正式请求预算、预热/预填充预算和采集要求；由后端 validate/plan 返回作为依据。

桌面右侧放 280–320px 的执行计划摘要，主要表单占余下空间；窄屏堆叠。单次简单任务保持单页填写，不强制每类任务都走多步向导。

按钮文案区分“校验配置”“预览计划”“加入队列”。提交成功反馈“已加入队列 · 第 N 位”，提供“查看任务”和“继续创建”；保留表单草稿。能力探测失败区分“执行器未安装”和“无法连接服务”，避免所有情况都显示为 AIPerf 不可用。

## 8. 统一性能结果：单次测试与负载扫描

### 8.1 第一屏给出性能与可信度

统一报告头：alias / model、Endpoint、测试时间、负载模式和执行配置摘要；执行后端及其版本作为次级元信息。主要操作为“查看关联任务 / 复制配置”，HTML 报告为次级动作。同一种测试类型的 AIPerf 和 EvalScope 结果使用相同页面结构。

首屏默认概览，固定顺序展示：

- **质量条**：结果完整 / 部分可用 / 不可用于结论，附原因和缺失范围；与是否执行成功独立。
- **指标条**：请求成功率、请求吞吐 req/s、平均 TTFT、尾延迟（P95 或 P99，明确是哪一个）。
- **上下文**：请求数 n、concurrency 或请求速率、输入/输出规模、测量来源与单位。没有数据的字段写“未采集”及原因。
- **观察结论**：只陈述数据支持的事实，例如“3/100 请求失败”；用户未设阈值时，不给“性能优秀/达标”评价。

当前 `summary_rows` 已带 sample_counts，应将计数纳入指标说明。现有 summary 提供平均值和 P99；需要 P95 时从已有 runs 数据读取或扩充统一投影，不能将 P99 改名 P95。没有服务端数据时，不影响客户端指标可读性。

### 8.2 分页职责

| 分页 | 内容 |
| --- | --- |
| 概览 | 核心指标、质量、工作负载、简短配置 |
| 延迟分布 | 指标 × P50/P95/P99 表和有明确单位的分布/分位图 |
| 请求明细 | 失败筛选、请求 ID、延迟、TTFT、输入/输出，点击展开原始记录 |
| 节点指标 | 节点窗口、覆盖、新鲜度、时间序列、指标字典 |
| 配置与产物 | 完整只读配置、哈希、原始字段、HTML/下载入口 |

多点扫描按实际保存的负载点显示曲线，不按执行后端限制分析入口；单次运行不制造“趋势”。input-only、decision、embedding 等任务继续按能力隐藏生成延迟。切换单位只在展示层转换，不改原始值；统一通过 `MetricSemantics` / `formatMetric`，明确 ms、s、req/s、tokens/s。

NVIDIA 的客户端性能指标与节点指标是不同数据源；TTFT、请求延迟、token 间延迟也不是同一个概念。界面优先使用本项目归档中的 source、scope、unit、executor_version 解释口径，官方文档作为说明补充，不覆盖已保存版本的定义。

## 9. 统一性能结果：缓存实验分析模块

本节描述缓存实验这种测试类型的扩展模块。当前实现来自 AIPerf 后端，但产品入口仍归属“性能测试结果”；未来其他后端具备相同实验能力时复用这些模块。

### 9.1 页面结构

```text
性能测试结果 / 缓存实验 / Qwen 前缀复用扫描
[执行完成] [结果部分可用]  已完成 11/12 组    AIPerf · 版本

[总览] [场景矩阵] [对比分析] [节点指标] [配置与产物]

场景矩阵
目标复用比例 ▾   负载 ▾   重复轮次 ▾   状态 ▾
```

大屏矩阵旁可出现 420–520px 详情区域；不足以让两侧都清楚展示时，点击进入独立子运行视图或覆盖抽屉。避免把窄列强塞到 1024px，也避免选中后仍需越过多个分析模块向下寻找。

URL 保存 `tab`、`subrun`、`baseline`、`candidate` 和必要筛选条件；选中态高亮，切换数据时清除旧详情并呈现新项骨架，防止旧请求内容短暂显示在新子运行标题下。

### 9.2 全局总览与当前页统计分开

实验级概览先展示计划组数、已完成组数、失败组数、各质量数量。完成组数可从实验 state 得到；跨全部组的结果指标和质量汇总需后端提供有范围说明的摘要。

现有“当前加载组 TTFT 的简单均值”从首屏移除，或明确放在矩阵区命名为“本页组均值”，不称作实验总体 TTFT。矩阵翻页不能改变实验级 KPI。

后续汇总规则：

- 请求成功率按总成功请求 / 总正式请求计算，注明有效范围，不平均每组百分比。
- 请求级均值需有有效样本数且 source/scope/unit 一致才可加权；否则只展示“各组均值范围”。
- P95/P99 不能简单平均或加权成总体分位数；需要合并原始观测或兼容直方图重算。暂不具备时只展示分组分位数。
- 不同负载、目标复用率和输入规模默认分组分析，不用一个总均值掩盖实验维度。
- 未读取、加载失败、未完成、未采集、无效数据分别标识；不填零。

### 9.3 三种比例始终分列

| 名称 | 含义 | 展示建议 |
| --- | --- | --- |
| 目标前缀复用率 | 用户配置的实验目标 | 计划值 |
| 实际生成复用率 | 输入生成后测得的比例 | 附工作负载模式与计算口径 |
| 服务端缓存命中率 | 服务端报告的缓存使用观测 | 附覆盖请求、来源和分母 |

节点 lookup-token hit ratio 与逐请求缓存使用也不是同一个分母。不得与上面三者折叠成一个“缓存命中”指标。保留命名空间不能证明缓存已清空、节点共享流量不能等同逐请求 P/D 耗时的现有约束，但将文字移至相关指标说明与质量条，不在每个模块重复长段警告。

### 9.4 矩阵与图表

默认列收敛到身份维度、状态、质量、TTFT、吞吐和服务端缓存；覆盖数、输入输出、种子等通过列设置或行展开查看。固定身份列和表头，长表只在表格容器内横向滚动。

提供“固定负载看复用率”“固定复用率看负载”两种分析。横轴必须显示真实数值与单位，纵轴显示指标与单位；tooltip 给出子运行、轮次、source、scope、n、quality。缺失点留空，invalid 点不参与结论，partial 点标记限制。多轮先展示散点和组内范围，不默认画平滑趋势线。

初版明确图表只覆盖当前加载范围；需要跨页完整图时添加专用聚合/序列接口，不在浏览器瞬间请求所有 scenario。单纯把散点改成热力图不能解决语义或范围问题。

### 9.5 对比分析

基线/候选使用固定选择条，显示可读场景身份与 task_id，而不是只显示原始 ID。选择后能直接跳转对比页或分页，清除选择只清除本地选择。

保留现有 `cacheComparison` / `comparableMetric` 门禁，兼容性信息就近展示：同执行器版本、同 source/scope/unit、同负载/输入/输出及实验语义。不同目标复用率用于复用收益对比；不同负载用于容量分析，应明确对比目的与其他固定条件。跨实验继续核验输入指纹与计划上下文。

延迟降低与吞吐提高的改善方向不同；用“下降/上升 + 数值 + 方向标签”，不能统一用正百分比代表变好。基线为零、缺值或不可比时显示不可计算及原因，不出现 Infinity。没有足够重复轮次时不宣称统计显著。

### 9.6 节点分析

先呈现节点选择、角色（单体/Prefill/Decode）、采样覆盖、窗口和采集状态，再给常用指标和时间序列。完整 labels、原始名、版本、边界、纳秒时间放到展开详情。

优先显示等待请求、运行请求、KV 占用、缓存观测等已由当前引擎解析器可靠支持的指标；不能假定所有节点都有 GPU 利用率。时间轴使用可读本地时间，原始 ns 可复制。采样缺口断线，提示峰值是样本峰值，直方图分位数是近似值；不能从节点相关性直接宣布根因。

请求级来源和节点级来源分组呈现。节点数据缺失时告诉用户是“未配置采集”“采集失败”“窗口覆盖不足”还是“引擎语义未支持”，并给相应下一步。

## 10. 后端与前端依赖

### 10.1 可直接使用现有契约的改动

- 执行中/排队分组计数、独立状态 badge、排队位置、AIPerf engine 标签、阶段与完成组数。
- 压缩连接编辑区、将新建与监控分离、给任务详情增加路由。
- 单次报告默认概览、显式 quality 条、sample_counts 说明。
- 缓存实验分页组织、选中高亮、基线/候选固定摘要、当前页统计范围命名。
- 日志自动跟随控制、局部错误状态、已有指标/请求的按需加载。
- 活跃实验定时刷新现有 state，并在新子运行完成时刷新当前可见数据；终态后停止轮询。

### 10.2 必须补充的能力

以下为建议契约，不是当前已有 API：

| 能力 | 建议 | 关键边界 |
| --- | --- | --- |
| 任务历史 | `GET /api/v1/tasks?status=&kind=&engine=&q=&cursor=&limit=` | 服务端分页与筛选；返回稳定排序；历史来源需持久化 |
| 统计 | `GET /api/v1/tasks/summary?from=&to=` | 明确全局/筛选范围、时间区间与任务去重规则 |
| 执行容量 | 任务运行信息接口，返回 backend、reachable、worker_count、busy_slots、observed_at | Redis 必须读真实 Worker；无法确定时字段为空 |
| 可复现配置 | 分类型脱敏快照 + plan 引用 | 不存前端秘密草稿，不把密钥带入分享链接 |
| 终态详情 | 完整投影 finished_at、脱敏 error 摘要、结果可读性 | 模型已有字段不等于每个分支都填值；`_saved_task_info()` 当前未投影全部终态字段 |
| 实验全局摘要 | summary + coverage + 各指标 source/scope/unit/n/availability | 与矩阵分页解耦；缓存按任务修订版本失效 |
| 时间线 | 可持久化阶段事件（后续） | 现有时间戳只能表达提交/开始/结束；不能伪造完整历史阶段 |

历史实现可先对现有 manifest 建立缓存索引或分页适配，避免每个浏览器每 5 秒递归扫描整个 outputs；长期随现有 submit/finish 写入可查询持久化索引。Redis RQ 的结果保留期不能当作长期任务历史。并发写入、索引重建、旧数据迁移需要单独设计。

所有成功 JSON 响应继续使用 `evalscope/service/api_models/` 的 Pydantic 模型和 `json_response()`，运行 `npm run contracts:generate` 更新前端契约；不手写 generated 文件。首次只做结构优化也不要引入第二套 API 客户端或状态机。

### 10.3 数据读取与状态组织

保持 `useAsyncResource` 作为数据读取入口；现有轮询可组合成任务状态适配层。列表共享一份快照、详情共享一份任务数据，避免相同 task_id 被头部、日志页和实时区重复请求。

当前 TaskRunMonitor 的 task/log 轮询未受 active 参数控制，而 AIPerf 实时面板受 active 控制；任务类型面板 keepMounted 后，隐藏页仍可能轮询。迁移时明确：仅可见详情持续读取日志和重指标，任务中心保留轻量列表同步。标签页后台降低频率，回到前台立即更新；请求失败退避，恢复后清除 stale。轮询不请求重叠、可取消旧请求。

先使用现有约 5 秒轮询，不以引入 WebSocket/SSE 作为布局改造前置条件。确有更低延迟需求再增加事件流，仍保留重连与轮询回退。

## 11. 视觉、响应式与可访问性

沿用 `DESIGN.md`：紫色用于主动作与选中态；success/warning/danger/info 用于业务状态；不让所有任务行都被品牌紫色填满。任务状态组件不复用分数色阶。

- 标题/正文/辅助文字继续使用 `type-*`；数值用 tabular-nums；ID/endpoint 用 mono。主要任务名和状态保持 14px 可读，不把密集等同缩小字号。
- 外边距约 24px、模块间距 16–24px、行间距由密度切换控制；桌面正常行高约 64px，紧凑约 52px，触摸目标保持约 44px。
- ≥1280px 可用列表 + 就近详情；1024px 以单主区为主；768px 以下统计折为两列，任务表转摘要卡；375px 保留任务名、状态、进度/等待、详情操作。
- sticky 标题与操作区要避开 52px 顶栏；避免多个长 sticky 容器相互遮挡。
- 状态用文字 + 图标，颜色不是唯一信号；不定进度不声明虚假 aria-valuenow。
- 仅在状态变化与关键阶段更新时 `aria-live="polite"` 通知，禁止每轮日志整段播报；保留现有 Tabs 的键盘导航。
- 打开详情后焦点进入标题，关闭后回到对应行；轮询不移动焦点。确认框、抽屉支持 Escape、焦点恢复和完整键盘操作。
- 支持 reduced-motion；两主题分别检查实际对比度，沿用 tokens 并不自动等于所有组合都合格。

## 13. 验收与验证计划

### 13.1 可观察的产品目标

以下为待验证目标，不是已测量提升：

- 用户进入任务中心后 5 秒内，能正确说出执行中与排队数量；用 5 位目标用户做任务式验证。
- 从任务列表到具体日志或结果不超过 2 次操作。
- 10 个以上混合状态任务时，无需逐行打开即可找到排队、停止中和失败任务。
- 缓存实验矩阵翻页时，实验全局摘要保持不变；当前页指标始终有范围标签。
- 任意 partial/invalid 结果第一次打开就能看见质量与原因入口。
- 刷新/分享任务链接后恢复同一任务；返回列表保留筛选和滚动。
- 不依赖颜色、鼠标 hover 或精细点击也能完成查看、停止和返回。

### 13.2 场景清单

| 场景 | 必须验证 |
| --- | --- |
| 0 个任务 | 数量为零与同步失败明确区分；主动作清楚 |
| 1 执行 + 3 排队 | 计数与 FIFO 位置正确；取消后位置更新；无假进度 |
| 多任务同模型/不同 Endpoint | alias、endpoint 和 ID 能区分，停止目标不会跟随草稿改变 |
| finalizing / cancelling | 不被 100% 或停止 ACK 误判完成；仍能看日志 |
| 请求提交超时 | 原 task_id 可追踪，不鼓励无条件重复提交 |
| completed + partial / invalid | 执行状态与质量独立；缺值不填零；结果限制醒目 |
| 刷新或关闭后再打开 | 终态任务可发现，配置摘要来自服务快照 |
| 内存服务重启 / Redis Web 重启 / Worker 丢失 | 按后端真实能力显示未知/恢复；不把队列可连接等同可执行 |
| 实验 >50 组 | 分页不改变全局摘要，对比身份稳定，按需加载 |
| 切换子运行时请求未完成 | 不显示旧数据到新标题，不应用过期响应 |
| 明细/节点接口失败 | 局部重试，其他区域可继续使用 |
| 无节点采集 / 采样缺口 | 可读原因与下一步，客户端结果仍可查看 |
| 同类型测试使用不同后端 | 共用性能结果列表与详情结构；后端只在元信息和可选筛选中体现 |
| 同一后端不同采集能力 | 分页按实际能力显示；已配置但采集失败与未配置明确区分 |
| 用户向上读日志 | 新日志不抢滚动；能恢复跟随 |
| 375/768/1024/1440px + 双主题 | 无整页横向溢出、遮挡或动作丢失；键盘和焦点正常 |
